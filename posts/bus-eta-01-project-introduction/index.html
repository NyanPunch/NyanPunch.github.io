천안 버스 ETA 프로젝트 ① — 예측 모델보다 데이터 수집부터 시작한 이유

차량 ID 없이 버스 도착정보를 연결하려면 무엇부터 준비해야 할까? 천안 버스 ETA 프로젝트의 목표와 데이터 수집부터 시작한 이유를 정리합니다.

2026.11.124분 읽기NyanPunch

버스 도착정보 API에는 “몇 초 뒤 도착하는지”, “몇 정류장 전에 있는지” 같은 정보가 담겨 있다. 이 정보를 시간순으로 모으면 버스의 이동을 추적하고 도착시간을 예측하는 데 활용할 수 있지 않을까?

bus-eta-predict는 이 질문에서 출발한 프로젝트다. 천안시 버스 도착정보를 수집하고, 여러 시점과 정류장의 관측을 연결해 버스 운행을 추적하는 기반을 만드는 것이 목표다.

다만 프로젝트 이름에 ETA가 들어간다고 해서 처음부터 예측 모델을 학습한 것은 아니다. 먼저 해결해야 할 문제는 API 응답을 어떤 의미의 데이터로 해석할 것인가였다.

도착정보 한 줄은 버스 한 대의 고유한 기록일까?

이 프로젝트의 출발 조건은 도착정보 관측을 연결할 때 차량 ID에 의존하지 않는다는 것이다.

예를 들어 한 정류장에서 다음과 같은 정보가 반복해서 들어왔다고 하자.

관측 시점 노선 남은 정류장 수 도착 예정시간
첫 번째 조회 7번 5개 300초
두 번째 조회 7번 4개 260초

두 관측은 같은 버스를 나타낼 가능성이 있다. 하지만 값이 비슷하다는 이유만으로 같은 버스라고 확정할 수는 없다. 같은 노선을 운행하는 다른 버스가 있을 수도 있고, 원천 정보의 갱신이 늦을 수도 있기 때문이다.

반대 상황도 있다. 서로 다른 두 정류장에서 받은 도착정보가 실제로는 같은 버스를 가리킬 수 있다. 따라서 응답 항목을 모두 별개의 버스로 세는 방식도 적절하지 않다.

이 프로젝트에서 추적하려는 대상은 우선 **여러 관측을 연결한 운행 기록인 track**이다. 이 기록이 특정 물리적 차량의 하루 전체 운행과 같다는 보장은 두지 않았다.

처음부터 노선 전체를 다루지 않았다

초기 대상은 천안시의 2번, 5번, 7번 노선이다. 여기서 노선번호는 세 개지만 실제 분석 대상 route_id는 네 개다. 조회 결과에서 5번이 서로 다른 두 ID로 구분됐기 때문이다.

같은 번호라는 이유로 두 경로를 합치거나, 번호만 보고 방향을 추정하지 않았다. 우선 API에서 받은 노선 ID와 경유 정류장 목록을 각각 보존하는 방식으로 시작했다.

관측 정류장도 처음에는 두 곳으로 제한했다. 이 두 곳에서 노선의 모든 버스를 볼 수 있다고 가정하지는 않았다. 작은 범위에서 응답 구조와 저장 흐름이 실제로 연결되는지 먼저 확인하기 위한 선택이었다.

API에서 안 보인다는 것이 운행하지 않는다는 뜻은 아니다

관측 데이터를 다룰 때 가장 조심한 부분은 ‘정보가 없음’의 해석이다.

조회 결과에 버스가 나타나지 않는 이유는 여러 가지일 수 있다.

  • 해당 조회 범위에 도착정보가 없을 수 있다.
  • API 요청이나 응답 파싱이 실패했을 수 있다.
  • 여러 페이지 중 일부만 수집했을 수 있다.
  • 관측하는 정류장에서 아직 확인할 수 없는 버스일 수 있다.

이 상황을 모두 “버스가 없다”로 처리하면, 수집 과정의 문제를 운행 상태로 잘못 해석하게 된다.

그래서 정상적인 빈 응답, 통신 오류, API 오류, 불완전한 페이지 수집을 구분해 기록하기로 했다. API 목록에서 사라졌다는 이유만으로 도착이나 결행을 확정하지 않는 것도 같은 이유다.

개발 순서는 원본에서 예측으로

전체 흐름은 다음과 같이 잡았다.

제한된 API 수집
    ↓
요청·응답 원본 저장
    ↓
관측 데이터 정규화
    ↓
시간순 재생과 버스 추적
    ↓
실제 도착 정답 확보
    ↓
ETA 예측과 평가

이 순서의 핵심은 원본을 남기는 것이다. 정규화나 추적 알고리즘을 수정했을 때, 같은 입력으로 다시 실험할 수 있어야 한다.

현재 저장소에는 실제 수집·저장과 오프라인 추적 재생까지 연결돼 있다. 온라인 상시 추적과 실제 도착 정답을 이용한 ETA 모델은 후속 단계다.
