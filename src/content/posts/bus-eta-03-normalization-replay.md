원본 응답을 DB에 저장하고 나면, 그 데이터를 추적 엔진에서 사용할 형태로 바꿔야 한다.

그 과정에서 중요한 것은 모든 값을 억지로 완성하는 일이 아니었다. **계산할 수 있는 관측과, 아직 판단할 수 없는 관측을 구분하는 것**이었다.

이번 단계에서는 저장된 도착정보를 정규화하고, 같은 입력으로 반복 실험할 수 있는 `replay` 명령을 만들었다.

## 남은 정류장 수를 노선 위 위치로 바꾸기

도착정보에는 조회 대상 정류장까지 몇 정류장이 남았는지를 나타내는 `arrprevstationcnt`가 있다.

노선 경유 목록에서 대상 정류장의 순서를 알면, 다음 식으로 버스 위치의 후보를 계산할 수 있다.

```text
추정 버스 순서 = 대상 정류장의 방문 순서 − 남은 정류장 수
```

예를 들어 대상 정류장이 노선에서 20번째이고, 남은 정류장 수가 4라면 위치 후보는 16이 된다.

```text
20 − 4 = 16
```

이 값은 지도 위 GPS 좌표가 아니다. 노선의 정류장 순서 축에서 계산한 근사치다.

정류장 사이의 거리도 서로 다르므로 이 위치의 변화량을 그대로 실제 이동거리나 속도로 해석할 수 없다. 남은 정류장 수의 집계 기준 역시 추가 검증이 필요하다.

그래서 정규화된 위치에는 다음 품질 플래그를 붙였다.

```text
position_semantics_unverified
```

계산 결과를 제공하면서도, 그 결과가 어떤 가정에 기대고 있는지 함께 남긴 것이다.

## 결측값을 0으로 바꾸면 잘못된 위치가 생긴다

남은 정류장 수가 없는 관측을 0으로 채우면 어떤 일이 생길까?

```text
대상 정류장 순서 − 0 = 대상 정류장 순서
```

정보가 없는 관측이 갑자기 “대상 정류장에 도착한 버스”처럼 바뀐다.

이를 피하기 위해 남은 정류장 수가 없거나 잘못된 값이면 `unresolved`로 남겼다. 음수이거나 계산 결과가 노선 범위를 벗어나는 경우도 강제로 보정하지 않는다.

반면 도착 예정시간인 `arrtime`이 잘못됐더라도, 남은 정류장 수와 경유 목록으로 위치를 계산할 수 있다면 위치 정규화는 허용한다. 이때 `arrtime`은 `null`로 두고 품질 플래그를 기록한다.

즉, 필드 하나의 오류 때문에 관측 전체를 무조건 버리지는 않되, 잘못된 값을 정상값처럼 사용하지 않도록 했다.

## 정류장 ID 하나가 방문 지점 하나를 뜻하지 않을 수 있다

순환하거나 일부 구간을 다시 지나는 노선에서는 같은 정류장 ID가 경유 목록에 여러 번 나타날 수 있다.

가령 경유 목록이 다음과 같다고 하자.

```text
A → B → C → A → D
```

단순히 `정류장 ID → 순서` 형태로 저장하면, 앞의 A 또는 뒤의 A가 덮어써질 수 있다.

따라서 같은 정류장 ID에 해당하는 방문 순서 후보를 모두 보존했다. 현재 정보만으로 어느 방문 지점인지 구분할 수 없으면 하나를 임의로 선택하지 않고 보류한다.

추적 과정에 잘못된 위치를 넣는 것보다, 현재의 불확실성을 드러내는 편이 낫다고 판단했다.

## 과거 관측에는 당시 확보한 경유 목록을 사용한다

노선 경유 목록은 바뀔 수 있다. 과거 도착정보를 현재의 경유 순서로 해석하면 당시와 다른 위치가 계산될 수 있다.

그래서 메타데이터의 내용 버전과 조회 이력을 구분해 저장하고, 재생할 요청의 시작 시점까지 확보된 최신 버전을 선택한다.

과거 시점에 사용할 수 있는 버전이 없다면, 나중에 조회한 버전으로 채우지 않고 미해결 상태로 남긴다.

여기서도 한계는 있다. 조회 이력을 보존한다고 해서 실제 노선 변경 시점을 모두 알 수 있는 것은 아니다. 확보하지 못한 과거 정보까지 복원할 수는 없다.

## API를 다시 호출하지 않는 재생 도구

정규화 규칙을 수정할 때마다 API를 다시 호출하면 입력 데이터가 달라진다. 알고리즘 변경의 효과인지, 버스 상황이 바뀐 것인지 비교하기 어려워진다.

`replay`는 DB에 저장된 요청과 응답을 읽는다. API 키가 필요하지 않고 추가 호출 예산도 사용하지 않는다.

```powershell
# 원본과 파생 결과를 변경하지 않고 요약 확인
python -m bus_eta_predict.cli replay --summary-only

# 요청·관측 이벤트를 새 JSONL 파일로 출력
python -m bus_eta_predict.cli replay `
  --output data/replay-new.jsonl

# 정규화 결과를 별도 실행으로 DB에 저장
python -m bus_eta_predict.cli replay `
  --persist --summary-only
```

`--persist`를 사용하지 않으면 DB에 파생 결과를 쓰지 않는다. 저장하는 경우에도 기존 원본을 덮어쓰지 않고, 별도의 정규화 실행과 결과를 추가한다.

## 시간순 재생은 동시 관측을 만드는 작업이 아니다

재생에서는 기본적으로 응답 수신 시각을 기준으로 요청을 정렬한다. 같은 시각에는 요청 시각과 요청 ID, 응답 내 항목 순번으로 순서를 결정한다.

수신 시각은 원천 시스템이 정보를 생성한 시각과 다르다는 점도 구분해야 한다. 네트워크와 원천 시스템의 갱신 지연이 포함될 수 있기 때문이다.

또한 서로 다른 정류장의 응답을 한 시점에 관측한 것처럼 합치지 않는다. 이 단계는 실제 시간 간격만큼 기다리는 시뮬레이션도 아니다. 저장된 사건을 정해진 순서로 처리하는 도구다.

출력에는 세 종류의 이벤트를 넣었다.

| 이벤트 | 내용 |
|---|---|
| `request` | 요청 상태와 페이지 수집 완전성 |
| `observation` | 정규화 결과 또는 보류 사유 |
| `summary` | 처리 건수, 실행 상태, 결과 해시 |

빈 응답과 실패도 요청 이벤트로 남는다. 이를 버스 도착이나 결행 사건으로 변환하지는 않는다.

## 같은 데이터로 같은 결과가 나오는지 확인하기

재생 결과에는 요청·관측 이벤트로 계산한 SHA-256 해시를 남긴다. 실행할 때마다 달라지는 재생 실행 ID나 저장 여부는 이 해시에서 제외한다.

2026년 10월 31일 개발 기록에서는 저장된 도착정보 요청 6건을 두 번 재생했다.

| 항목 | 기록된 결과 |
|---|---:|
| 원본 응답 항목 | 72개 |
| 대상 노선의 정규화 관측 | 30개 |
| 다른 노선으로 분석 대상에서 제외 | 42개 |
| 추가 API 호출 | 0회 |
| 두 실행의 결과 해시 | 일치 |

대상에서 제외한 42개 항목도 원본에서는 삭제하지 않았다.

해시 일치는 같은 입력을 같은 방식으로 처리했다는 재현성의 근거다. 계산한 위치가 실제로 정확하다거나, 두 관측이 같은 버스라는 증거는 아니다.

여기까지의 결과물은 버스 추적을 반복해서 실험할 수 있는 입력 파이프라인이다. 다음 단계에서는 여러 정류장의 관측을 어떻게 연결하고, 후보가 여러 개일 때 어떻게 판단을 보류할지 다룬다.
