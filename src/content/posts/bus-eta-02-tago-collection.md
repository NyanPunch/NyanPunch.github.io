데이터 수집기를 만들 때 먼저 떠올리기 쉬운 구조는 단순하다.

```text
API 호출 → 필요한 값 추출 → DB 저장 → 반복
```

하지만 실제로 수집을 반복하려면 더 많은 상황을 고려해야 한다. 호출 한도에 도달하면 어떻게 할지, 응답이 여러 페이지라면 어디까지 성공으로 볼지, 요청은 성공했지만 저장에 실패하면 어떻게 할지 정해야 한다.

이번 단계에서는 수집 범위를 제한하고, **받은 응답을 나중에 다시 해석할 수 있도록 저장하는 것**에 집중했다.

## 비동기 수집기지만 요청은 한 번에 하나씩

수집기에는 `aiohttp`를, PostgreSQL 연결에는 `psycopg`를 사용했다.

비동기 클라이언트를 사용했지만 초기 요청 동시성은 1개로 제한했다. 시작부터 처리량을 높이기보다 요청 순서, 응답 상태, 호출량을 확인하기 쉬운 구조를 택했다.

기본 수집은 1회 순회 후 종료한다. 실행만 해 두면 계속 API를 호출하는 방식으로 만들지 않았다.

반복 수집이 필요할 때는 횟수와 간격, 실행 중 최대 호출 수를 명시한다.

```powershell
python -m bus_eta_predict.cli collect `
  --cycles 3 `
  --interval 10 `
  --max-requests 10
```

위 명령은 설정된 정류장을 10초 간격으로 3회 순회하도록 요청하되, 페이지 조회와 재시도를 포함한 호출 수는 최대 10회로 제한한다.

## 호출 간격보다 먼저 예상 호출량을 계산했다

정류장 하나를 10초마다 하루 동안 조회하면 기본 호출량만 다음과 같다.

```text
86,400초 ÷ 10초 = 8,640회
```

관측 정류장을 늘리거나 응답이 여러 페이지로 나뉘면 호출량도 늘어난다. 재시도와 메타데이터 조회도 추가된다.

그래서 두 종류의 제한을 뒀다.

| 제한 | 목적 |
|---|---|
| 실행별 최대 호출 수 | 한 번의 실험에서 사용할 호출량 제한 |
| 서비스별 일일 호출 수 | 여러 실행에 걸친 하루 사용량 제한 |

일일 사용량은 프로세스 메모리가 아니라 PostgreSQL에 저장한다. 프로그램을 다시 실행해도 이미 사용한 예산을 이어서 계산하기 위해서다.

기본 일일 상한은 서비스별 500회로 설정했다. 이 값은 실제 계정 한도를 확인한 결과가 아니라, 초기 실험을 위한 자체 제한이다.

호출 예산은 네트워크 요청 전에 예약한다. 예약 직후 프로세스가 종료되면 실제 요청 없이 사용량이 남을 수 있지만, 호출량을 적게 계산하는 상황을 피하는 쪽으로 설계했다.

## HTTP 200만으로 성공을 판단하지 않았다

HTTP 요청이 성공했어도 응답 본문에 인증 오류나 서비스 오류가 들어 있을 수 있다. 따라서 HTTP 상태와 API 결과 코드를 함께 확인한다.

수집 결과는 다음과 같이 구분했다.

| 상태 | 의미 |
|---|---|
| `success_nonempty` | 정상 응답이며 항목이 있음 |
| `success_empty` | 정상 응답이며 항목이 없음 |
| `transport_error` | 타임아웃 등 통신 오류 |
| `http_error` | HTTP 오류 응답 |
| `api_error` | API 본문에 보고된 오류 |
| `parse_error` | 응답 해석 실패 |

이 구분은 이후 분석에도 필요하다. 정상 빈 응답과 요청 실패를 같은 빈 목록으로 바꾸면, 버스가 관측되지 않은 이유를 되짚을 수 없기 때문이다.

재시도도 모든 실패에 적용하지 않았다. 타임아웃, 429, 5xx 등 일시적일 수 있는 오류에 한해 제한적으로 수행하고, 인증 오류는 실행을 중단하도록 했다.

## 가공한 값과 함께 요청의 맥락을 남겼다

주요 저장 테이블은 다음과 같다.

| 테이블 | 저장하는 내용 |
|---|---|
| `collection_runs` | 수집 실행 설정과 종료 상태 |
| `api_requests` | 요청 시각, 응답 상태, 본문, 항목, 재시도 관계 |
| `api_daily_usage` | 서비스별 일일 호출 사용량 |
| `route_metadata_versions` | 노선 경유 목록과 내용 해시 |

`api_requests`에는 응답 항목뿐 아니라 요청·수신 시각, HTTP 상태, API 코드, 페이지 번호, 전체 항목 수 등을 함께 남긴다. 인증키는 저장하지 않고, 원문에 반사된 키도 마스킹하도록 처리했다.

응답을 받은 뒤에는 저장을 먼저 완료한다. DB 저장에 실패하면 다음 수집을 중단한다. 실시간으로 바뀌는 API 응답은 나중에 다시 호출해도 같은 내용을 얻는다는 보장이 없기 때문이다.

## 페이지를 전부 받았는지도 별도로 기록했다

여러 페이지로 나뉜 응답은 페이지별 요청이 성공했다고 끝나는 것이 아니다. 전체 항목 수가 일관되는지, 예상한 항목을 모두 받았는지도 확인해야 한다.

이를 `batch_complete`로 기록했다.

다만 `batch_complete=true`는 페이지 수집이 일관되게 끝났다는 뜻이다. 모든 페이지가 정확히 같은 순간의 원천 데이터를 담았다는 의미는 아니다. 페이지를 읽는 사이에도 도착정보는 바뀔 수 있다.

값이 같은 응답 항목도 임의로 제거하지 않았다. 값이 같다는 사실만으로 중복 전송인지, 서로 다른 버스인지 판단하기 어렵기 때문이다.

## 첫 실제 연결 검증 결과

2026년 10월 25일 개발 기록에는 다음과 같은 제한 실험이 남아 있다.

| 실험 | 호출 수 | 결과 |
|---|---:|---|
| 네 노선 ID의 경유 정류장 조회 | 4회 | 메타데이터 저장 |
| 두 정류장, 10초 간격으로 2회 순회 | 4회 | 도착정보 원본 저장 |

도착정보 응답 항목은 총 48개였고, 그중 분석 대상 네 노선 ID에 해당하는 항목은 20개였다.

여기서 **20개는 버스 20대가 아니라 관측 행 20개**다. 서로 다른 시점과 정류장에서 같은 버스를 관측한 내용이 포함될 수 있다.

이 실험으로 API 호출부터 원본 저장까지의 연결은 확인했다. 갱신 주기, 누락률, 시간대별 관측 범위까지 검증한 것은 아니다.

다음 단계는 이 원본을 다시 API에서 가져오지 않고 분석하는 것이다. 이를 위해 정규화와 재생 도구를 추가했다.
